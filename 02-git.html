Part 1

バージョン管理ってなに？

道具の使い方の前に、「何のための道具なのか」から始めます。

Step 1/ 11

そもそもバージョン管理とは？

「バージョン管理ツール」と聞くと難しそうですが、まずバージョンとは「ある時点のファイルの状態」のことです。レポートを書いて、直して、また直す。そのたびに新しいバージョンが生まれています。

バージョン管理とは、ファイルの変更を「いつ・誰が・何を・なぜ」変えたのか記録して、いつでも前の状態に戻せるようにすることです。

1 / 7手作業とバージョン管理

上のアニメーションの前半は、多くの人がやっている「手作業のバージョン管理」です。コピーが増えるほど、どれが最新で、何を変えたのかが分からなくなります。この記録を自動で、正確にやってくれるのが Git（ギット）というバージョン管理ツールです。

たとえると

ゲームのセーブポイントです。ボス戦の前にセーブしておけば、失敗してもそこからやり直せます。Git では、このセーブを「コミット」と呼びます。

補足

Google ドキュメントの「版の履歴」や、iPhone の写真の「編集を元に戻す」も、身近なバージョン管理の一種です。Git はこれを、プログラムのような文字のファイルに対して、もっと細かく、複数人でできるようにしたものです。

次へ：利点と欠点

Step 2/ 11

利点と欠点

便利な道具ですが、良いことばかりではありません。両方を知ったうえで使いどころを判断しましょう。

利点

  • いつでも過去に戻れる壊しても、動いていた時点に戻せる。安心して大胆に変更できる
  • 何が変わったかが1行単位でわかる「どこを直したか」を目で探す必要がない
  • 変えた理由が残るコミットごとにメッセージを書くので、半年後の自分や他人にも経緯がわかる
  • 複数人で同時に作業できるそれぞれの変更を、あとから1つにまとめられる
  • 試しの作業を安全にできる本体とは別の「枝」で実験して、うまくいったら取り込める
  • バックアップになるGitHub に置けば、PC が壊れても履歴ごと残る

欠点

  • 最初に覚えることが多いadd、commit、push などのコマンドや用語に慣れるまで時間がかかる
  • 記録する習慣が必要自動保存ではないので、こまめにコミットしないと履歴が粗くなる
  • Word・Excel・画像・動画などは苦手中身が文字ではないので、「何が変わったか」を表示できない。大きなファイルは容量も圧迫する
  • ぶつかったときに手で直す必要がある2人が同じ行を変えると「コンフリクト」が起き、どちらを残すか人が決める
  • うっかり公開すると取り返しにくいパスワードなどを記録して公開すると、消しても履歴に残る

ほかの方法と比べると、次のようになります。

コピーを保存クラウドの版履歴Git
過去に戻れる手作業できるできる
何が変わったかわかるできないざっくり1行単位
変えた理由が残るできないできないできる
複数人で同時に作業難しい同じ文書なら得意
覚えること少ない少ない多い

使いどころ

向いているもの：プログラム、Webページ（HTML・CSS）、Markdown のメモ、CSV のデータ、LaTeX の論文など、中身が文字のファイル。
向いていないもの：Word、PowerPoint、動画など。こちらはクラウドの版履歴のほうが楽です。

理解度チェック

Git が特に苦手なファイルはどれ？

中身が文字ではないファイルは、変更点を表示できず、容量も大きくなりがちです。

次へ：Git と GitHub の違い

Part 2

Git の基本

自分の PC の中で、変更を記録する方法を学びます。

Step 3/ 11

Git と GitHub の違い

名前が似ていますが、役割はまったく違います。

GitGitHub
正体ソフトウェア（道具）Web サービス
動く場所自分の PC の中インターネット上
できること変更の記録、履歴の表示、過去に戻る履歴の保管・共有、レビュー、Web 公開
ネットがなくても使える使えない

たとえると

Git はカメラ、GitHub は写真共有サービスです。写真を撮る（記録する）のはカメラだけでもできますが、みんなで見るにはアップロード先が必要です。

補足

GitHub と同じ役割のサービスに、GitLab や Bitbucket もあります。中で使われている Git は同じです。

次へ：3つの場所：編集・ステージ・リポジトリ

Step 4/ 11

3つの場所：編集・ステージ・リポジトリ

Git では、ファイルが3つの場所を順番に移動します。最初はここでつまずく人が多いので、アニメーションで動きを確認しましょう。

1 / 43つの場所
場所ひとことで入れるコマンド
作業ディレクトリいま編集しているフォルダ（ふつうに編集する）
ステージ次に記録するものを並べる台git add
リポジトリ記録（コミット）がたまっていく保管庫git commit

たとえると

記念写真です。git add は「写したい人を撮影台に並べる」こと、git commit は「シャッターを押して1枚残す」ことです。並べる人を選べるので、関係ない変更を一緒に記録せずにすみます。

次へ：はじめてのコミット

Step 5/ 11

はじめてのコミット

実際に手を動かして、最初の記録を作ってみます。最初に一度だけ、記録に残る名前とメールアドレスを設定します。

最初に一度だけ
git config --global user.name "あなたの名前"
git config --global user.email "you@example.com"

次に、フォルダを Git で管理する設定をして、ファイルを記録します。$ は入力する行の目印なので、打たなくて大丈夫です。

ターミナル
$ git init
Initialized empty Git repository in .../my-site/.git/

$ git status
# まだ記録されていないファイルが赤く表示される

$ git add index.html
$ git commit -m "トップページを作成"
[main (root-commit) a1b2c3d] トップページを作成
 1 file changed, 10 insertions(+)

$ git log --oneline
a1b2c3d (HEAD -> main) トップページを作成
コマンド意味
git initこのフォルダを Git で管理し始める（最初の1回だけ）
git statusいまの状態を確認する。迷ったらまずこれ
git add ファイル名ステージに置く。git add . ですべて
git commit -m "説明"説明をつけて記録する
git log記録の一覧を見る

ポイント

コミットメッセージは「何を・なぜ」が伝わるように書きます。「修正」「aaa」ではなく、「トップページの誤字を修正」「お問い合わせフォームを追加」のように。

補足

第0回の設定をしていない場合は、main ではなく master と表示されます。どちらも「基本の枝」の名前で、働きは同じです。GitHub に送る前に git branch -M main で名前をそろえます（Step 7）。

理解度チェック

git add のあとに、記録を残すために使うコマンドは？

add で並べて、commit で記録します。

次へ：履歴を見る・過去に戻る

Step 6/ 11

履歴を見る・過去に戻る

記録がたまってくると、Git の本当の力が発揮されます。「いつ壊れたか」「何を変えたか」を、履歴から探せるようになります。

1 / 4履歴をたどる
変更点を見る（git diff）
$ git diff
--- a/style.css
+++ b/style.css
-  color: blue;
+  color: bule;

赤い - の行が消えた内容、緑の + の行が加わった内容です。

コマンドできること
git log --oneline履歴を1行ずつ一覧で見る
git diffまだコミットしていない変更点を見る
git show IDあるコミットで何を変えたかを見る
git restore ファイル名まだコミットしていない変更を取り消して、最後の記録の状態に戻す

注意

git restore で取り消した変更は、記録されていないので元に戻せません。消してよいか、git diff で確認してから使いましょう。

補足

HEAD は「いま見ている場所」を指す目印です。コミットの ID（a1b2c3d のような文字列）は、記録ごとに付く指紋のようなものです。

次へ：GitHub と同期する：push と pull

Part 3

GitHub で共有する

記録をインターネットに置いて、仲間と共有・公開します。

Step 7/ 11

GitHub と同期する：push と pull

ここからは GitHub の出番です。手元の履歴を GitHub に置いておく場所のことを リモートリポジトリ と呼びます。

1 / 5push と pull
コマンド向き意味
git pushPC → GitHub自分のコミットをアップロードする
git pullGitHub → PCほかの人の変更を取り込む
git clone URLGitHub → PCリポジトリを履歴ごとまるごとコピーする（最初の1回）
はじめて GitHub に push するとき
$ git branch -M main
$ git remote add origin https://github.com/ユーザー名/my-site.git
$ git push -u origin main

補足

origin は「GitHub 上のリポジトリ」につけたあだ名です。2回目からは git push だけで送れます。

ポイント

作業を始める前に git pull、終わったら git push。これを習慣にすると、仲間との食い違いが起きにくくなります。

理解度チェック

GitHub にある最新の変更を、自分の PC に取り込むコマンドは？

pull は「引っ張ってくる」。push は「押し出す」です。

次へ：ブランチで安全に試す

Step 8/ 11

ブランチで安全に試す

ブランチ（枝）は、本体の流れを残したまま、別の作業をするための仕組みです。新しい機能を試すときは、枝を作ってその上で作業します。

1 / 5ブランチ
ブランチの基本操作
$ git switch -c feature   # 枝を作って移動する
$ git branch              # 枝の一覧（* がいまいる枝）
$ git switch main         # main に戻る
$ git merge feature       # feature の変更を main に取り込む

たとえると

レポートの下書き用のコピーです。下書きで思い切って書き直しても、提出用の原本は無事。良くなったら原本に反映します。

次へ：プルリクエストとコンフリクト

Step 9/ 11

プルリクエストとコンフリクト

チームで開発するときは、自分で直接 main にマージせず、プルリクエスト（PR）を作って確認をお願いします。「このブランチの変更を main に入れてもいいですか？」という依頼です。

  1. ブランチで作業してコミットし、GitHub に push する
  2. GitHub の画面で「Pull request」を作る
  3. 仲間が変更点を見て、コメントや修正の提案をする（レビュー）
  4. 問題がなければ、GitHub 上で「Merge」ボタンを押す

2人が同じファイルの同じ行を別々に変えると、Git はどちらを残すか決められません。これを コンフリクト（衝突）といい、ファイルに次のような印が入ります。

コンフリクトしたファイル
<<<<<<< HEAD
<h1>プレゼミへようこそ</h1>
=======
<h1>プレゼミの資料置き場</h1>
>>>>>>> feature

上が自分の変更、下が取り込もうとした変更です。残したい内容に書き換えて印の行を消し、git add と git commit をすれば解決です。

ポイント

コンフリクトは失敗ではなく、「人が判断してね」という Git からの合図です。こまめに pull し、同じ場所を同時に触らないよう声をかけ合うと減らせます。

理解度チェック

2人が同じ行を別々に書き換えて、まとめようとしたときに起きるのは？

どちらを残すか、人が選んで解決します。

次へ：公開してはいけないものを守る

Step 10/ 11

公開してはいけないものを守る

GitHub のリポジトリには 公開（Public） と 非公開（Private） があります。公開リポジトリは、世界中の誰でも中身と履歴をすべて見られます。

注意

パスワード、API キー、個人情報、アンケートの生データなどは、絶対にコミットしないでください。あとからファイルを消しても、過去のコミットの中に残り続けます。公開リポジトリでは、自動で鍵を探して悪用するプログラムも動いています。

記録したくないファイルは、.gitignore というファイルに名前を書いておくと、Git が無視してくれます。

.gitignore の例
# 秘密の設定（パスワードやキー）
.env
*.key

# 自動で作られるファイル
node_modules/
__pycache__/
.DS_Store
うっかりしたときやること
まだ push していないそのコミットをやり直す（先輩や先生に相談）
もう push してしまったファイルを消すだけでは不十分。そのパスワードやキーをすぐに無効化して作り直す

ポイント

git add . の前に git status で、何を記録しようとしているか必ず確認しましょう。第1回で学んだ「HTTPS で通信を守る」のと同じで、仕組みを知っていれば防げる事故です。

理解度チェック

パスワードを書いたファイルを公開リポジトリに push してしまった。最初にすべきことは？

履歴に残っているので、パスワード自体を使えなくするのが最優先です。

次へ：GitHub Pages で公開する

Step 11/ 11

GitHub Pages で公開する

GitHub には、リポジトリの HTML・CSS をそのまま Web サイトとして公開できる GitHub Pages という機能があります。第1回で学んだ静的なページを、無料で置いておける場所です。

  1. リポジトリに index.html を置いて push する
  2. GitHub のリポジトリ画面で「Settings」→「Pages」を開く
  3. 「Branch」で main と / (root) を選んで「Save」
  4. しばらくすると、次の URL でページが見られる
公開される URL
https://ユーザー名.github.io/リポジトリ名/

以後は、ファイルを直して commit・push するたびに、サイトが自動で更新されます。Git で記録して、GitHub で公開する。この流れが、このレッスンのゴールです。

注意

GitHub Pages のサイトは、誰でも見られる公開ページになります。前の段階と同じく、個人情報や秘密の情報は載せないようにしましょう。
