Overview

全体の流れ

Web に登場するのは、お願いする側・応える側・つなぐ道の3者だけです。

Wi-Fi、携帯の電波、光ファイバー、世界中のルーター

この「注文して、料理が届く」を細かく分けると、次の9段階になります。ボタンを押すと、データの小包（黄色い丸）が順番に動きます。

Step 1/ 9

URLを入力する

ブラウザ（Safari や Chrome）に入力する URL は、どのサーバーの、どこにあるデータを、どんな方法でもらうかを1行にまとめたものです。

https://スキーム
通信の方法
www.example.jpドメイン名
サーバーの名前
/news/パス
サーバーの中の場所

たとえると

手紙の宛名書きです。ドメイン名が届け先の建物、パスが建物の中の部屋、スキームが「書留で」のような送り方にあたります。

次へ：電波でインターネットへ出る

Step 2/ 9

電波でインターネットへ出る

スマホは電波でデータを送ります。Wi-Fi なら家や大学のルーターへ、4G・5G なら近くの基地局へ届き、そこから光ファイバーを通ってインターネットへ出ていきます。

インターネットは1本の線ではなく、世界中のルーターがつながった網です。データはパケットという小包に分けられ、ルーターからルーターへバケツリレーで運ばれます。

1 / 6パケットの旅

小包には宛先として IPアドレス が書かれています。ネットにつながる機器には、スマホも含めて必ず IP アドレスが割り当てられます。

補足

IPアドレスは 203.0.113.10 のように、0〜255 の数字を4つ並べた形が一般的です（IPv4）。数が足りなくなったため、より長い IPv6 も使われています。

次へ：DNSで住所を調べる

Step 3/ 9

DNSで住所を調べる

www.example.jp のような名前は人間が覚えるためのものです。コンピュータは相手を IP アドレスで探すので、最初に DNSサーバー へ「この名前の住所は？」と問い合わせます。

1 / 5DNSの問い合わせ
DNS への問い合わせ（イメージ）
# スマホ → DNSサーバー
www.example.jp の IPアドレスを教えて

# DNSサーバー → スマホ
www.example.jp は 203.0.113.10 です

補足

一度調べた結果はしばらく覚えておきます（キャッシュ）。同じサイトを2回目に開くときは、この段階を省略できることがあります。

たとえると

スマホの連絡先アプリ。「お母さん」という名前から電話番号を引くのと同じです。

理解度チェック

ドメイン名から IP アドレスを調べる仕組みはどれ？

DNS はインターネットの電話帳です。

次へ：TCPで接続する

Step 4/ 9

TCPで接続する

住所がわかったら、サーバーと確実に会話できる道をつくります。最初に3回あいさつを交わすので、3ウェイハンドシェイクと呼ばれます。

1 / 43ウェイハンドシェイク

TCP は、小包が全部届いたか確認し、欠けたら送り直し、順番を並べ直す係です。途中で小包が迷子になっても、ページが崩れずに届くのは TCP のおかげです。

補足

このとき ポート番号 で「サーバーのどの窓口か」も指定します。HTTPS は 443 番、HTTP は 80 番が決まりです。

理解度チェック

小包が途中で欠けても、ページが崩れずに届くのはどの技術のおかげ？

TCP が届いたかを確認し、欠けたものを送り直しています。

次へ：TLSで暗号化する

Step 5/ 9

TLSで暗号化する

アドレスバーの鍵マークは、この段階を通った印です（Chrome では鍵の代わりに、つまみの形をした「サイト情報」のアイコンが表示されます）。TLS は2つの仕事をします。

  • 本物か確かめる：サーバーが「証明書」を見せ、ニセモノのサイトでないことを確認します。
  • 中身を暗号化する：途中のルーターや同じ Wi-Fi の人に、中身を読まれたり書き換えられたりしないようにします。

注意

http://（s がない）で始まるサイトは暗号化されていません。パスワードや個人情報を入力しないようにしましょう。

補足

鍵マークが保証するのは「通信が守られていること」だけです。サイトの中身が安全かどうかまでは保証しません。

ポイント

初めて話す相手と、どうやって鍵を安全に共有するのか。そのしくみは後半の公開鍵暗号で詳しく見ます。

理解度チェック

https:// で始まるページ（Safari などでは鍵マークが付く）で、守られていることはどれ？

鍵マークは TLS の印です。サイトの中身の安全性は別の話です。

次へ：HTTPリクエストを送る

Step 6/ 9

HTTPリクエストを送る

いよいよ本題です。HTTP はブラウザとサーバーが話すためのルールで、実際に送られるのは次のような文字です。

HTTP リクエストの例
GET /news/ HTTP/1.1               # 何をしたいか
Host: www.example.jp              # どのサイトか
User-Agent: Mozilla/5.0 (iPhone ...)   # 誰が頼んでいるか
Accept: text/html                 # 欲しい形式

1行目の GET をメソッドといいます。まずは次の2つを覚えれば十分です。

メソッド意味使われる場面
GETくださいページを見る、画像を読み込む
POST受け取ってくださいログイン、フォーム送信、投稿
次へ：サーバーがページを用意する

Step 7/ 9

サーバーがページを用意する

サーバーといっても、中身は普通のコンピュータです。多くはデータセンターや、AWS などのクラウドの上で動いています。ページの用意のしかたは大きく2通りあります。

静的なページ動的なページ
しくみ用意してあるファイルをそのまま返すプログラムがデータベースを調べて、その場で作る
見え方誰が見ても同じ人や時間によって変わる
例大学の案内ページ、GitHub PagesSNS のタイムライン、ログイン後のページ

ポイント

第3回で学ぶ Python は、動的なページを作るプログラムによく使われる言語です。

次へ：HTTPレスポンスが返る

Step 8/ 9

HTTPレスポンスが返る

サーバーは、結果を表すステータスコードと、ページの中身（HTML）をセットで返します。

HTTP レスポンスの例
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html>
  <h1>お知らせ</h1> ...
コード意味よく見る場面
200成功ふつうに表示できたとき
301引っ越しましたURL が変わったページ
404見つかりませんURL の打ち間違い、消えたページ
500サーバー側の失敗プログラムのエラー

ポイント

最初の数字で見分けます。2 は成功、4 はお客さん（ブラウザ）側の問題、5 はお店（サーバー）側の問題です。

理解度チェック

URL を打ち間違えたときによく出るステータスコードは？

404 は「見つかりません」。4 で始まるのはブラウザ側の問題です。

次へ：ブラウザが表示する

Step 9/ 9

ブラウザが表示する

ブラウザは届いた HTML を上から読み、3種類の材料を組み合わせて画面を作ります。

材料役割たとえ
HTML見出し・文章・画像の場所家の骨組み
CSS色・文字の大きさ・配置内装
JavaScriptボタンを押したときの反応など電気や水道

HTML の中に「この画像も必要」「この CSS も必要」と書いてあると、ブラウザは段階6〜8を何度もくり返します。ふつうのページでも、表示までに数十回のやりとりがあります。

ポイント

本当に数十回も通信しているのか、次の演習1で自分の目で確かめてみましょう。

次へ：公開鍵暗号で、鍵を安全に渡す

Part 2

セキュリティのしくみ

Step 5 と、ログインの裏側をもう一歩くわしく見ていきます。

Security 1/ 2

公開鍵暗号で、鍵を安全に渡す

Step 5 で「中身を暗号化する」と書きました。暗号化するには、送る側と受け取る側が同じ「鍵」を持っている必要があります。では、初めて話す相手に、その鍵をどうやって安全に渡すのでしょうか。途中で鍵ごと盗まれたら意味がありません。

共通鍵暗号公開鍵暗号
鍵1つの鍵を両者で共有公開鍵と秘密鍵のペア
速さ速い遅い
弱点鍵を渡す途中で盗まれると終わり計算が重く、大量のデータには向かない

TLS は両方のいいところを組み合わせます。公開鍵暗号で共通鍵を安全に渡し、そのあとは速い共通鍵暗号で通信するという流れです。

1 / 7鍵の受け渡し

たとえると

公開鍵は「誰でも閉められるけれど、持ち主しか開けられない南京錠」です。南京錠そのものは配っても困りません。開けるためのカギ（秘密鍵）はサーバーの外に出ません。

補足

届いた南京錠が本当に www.example.jp のものかは、認証局（CA）という第三者が証明書で保証します。これが Step 5 の「本物か確かめる」の正体です。

もう少し正確に

実際の TLS 1.3 では、共通鍵を箱に入れて送るのではなく、「鍵交換」という方法で両者が同じ共通鍵を計算して作ります。それでも「公開鍵のしくみを使って、盗み見されずに共通鍵を共有する」という考え方は同じです。

理解度チェック

この仕組みで、ロックされた箱を開けられるのは誰？

秘密鍵はサーバーの外に出ないので、開けられるのはサーバーだけです。

次へ：セッションとCookieで、ログインを保つ

Security 2/ 2

セッションとCookieで、ログインを保つ

HTTP には「前のやりとりを覚えていない」という性質があります（ステートレス）。毎回が初対面なので、このままではログインしても、次のページで「どなたですか？」と聞かれてしまいます。

そこで使うのが セッション と Cookie です。ログインに成功すると、サーバーは「セッション ID」という番号札を発行し、ブラウザはそれを Cookie として保存します。以後のリクエストに番号札を添えることで、サーバーは「さっきの人だ」とわかります。

1 / 6ログイン状態のしくみ
実際にやりとりされるヘッダー
# ログイン成功時のレスポンス
HTTP/1.1 200 OK
Set-Cookie: sid=a8f3...; Secure; HttpOnly

# 次のリクエスト
GET /mypage HTTP/1.1
Cookie: sid=a8f3...

たとえると

コートを預けたときにもらうクロークの番号札です。札を見せれば、毎回名前を名乗らなくても自分のコートが出てきます。

注意

セッション ID は「ログイン済みの証」です。盗まれると、パスワードを知らなくても本人になりすまされます（セッションハイジャック）。HTTPS で通信を暗号化するのは、これを防ぐためでもあります。

補足

上のヘッダーの Secure は「HTTPS のときだけ送る」、HttpOnly は「JavaScript から読めなくする」という設定です。どちらも番号札を盗まれにくくする工夫です。

身を守るために

  • 共用の PC では必ずログアウトする（サーバー側のセッションが消える）
  • https:// で始まらないページでログインしない
  • パスワードを使い回さず、二段階認証を使う

理解度チェック

ログイン後、ブラウザがリクエストのたびに自動で送っているものは？

Cookie に入ったセッション ID を毎回添えることで、ログイン状態が続きます。
