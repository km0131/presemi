Part 1

データを設計する

研究の問いから、何を・どんな形で記録するかを決めます。

Step 1/ 12

問いから、集めるデータを決める

システムを作る前に、何を記録すればリサーチクエスチョンに答えられるかを決めます。ここがあいまいなまま作り始めると、集め終わってから「あの項目も取っておけばよかった」となり、やり直しがききません。

このページでは、研究の流れで使った例を続けます。

1 / 4問いからテーブルへ
決めること例
誰から大学生 10人
いつ・何回14日間、1日1回
どうやって参加者が自分のスマホから記録フォームに入力
何を参加者ID、何日目、問題数、正答数、かかった時間、難しさの感じ方

ポイント

計算で出せるものは、元の数字を記録するのが基本です。「正答率 80%」ではなく「20問中16問」を記録しておけば、あとから正答率も誤答数も計算できます。

注意

「念のため」と項目を増やしすぎると、参加者の負担が増えて記録漏れの原因になります。問いに必要なものを中心に、多くても1回1〜2分で入力できる量にしましょう。

次へ：テーブルを設計する

Step 2/ 12

テーブルを設計する

決めた項目を、データベースのテーブルにします。参加者の表と記録の表に分けるのがポイントです。

schema.sql
-- 参加者（名前は入れない）
CREATE TABLE IF NOT EXISTS participants (
    participant_id TEXT PRIMARY KEY,      -- 例：P01
    consented_at   TEXT NOT NULL          -- 同意した日
);

-- 毎回の記録（1回の練習 = 1行）
CREATE TABLE IF NOT EXISTS records (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    participant_id TEXT    NOT NULL REFERENCES participants(participant_id),
    day            INTEGER NOT NULL,      -- 何日目か（1〜14）
    total          INTEGER NOT NULL,      -- 問題数
    correct        INTEGER NOT NULL,      -- 正答数
    seconds        REAL    NOT NULL,      -- かかった時間（秒）
    difficulty     INTEGER,               -- 難しさ 1〜5
    created_at     TEXT DEFAULT CURRENT_TIMESTAMP
);
設計のコツ理由
1行 = 1回の記録にする14日分を1行に横並びにすると、集計しにくく、日数を変えられない
名前ではなく ID で記録する記録の表だけを見ても、誰のデータかわからないようにする（Step 4）
数値は数値の型で保存するINTEGER・REAL にしておけば、そのまま計算できる
記録した日時を自動で残すあとから「いつ入力されたか」を確かめられる

補足

この「1行が1件の観測」という形は、分析の世界では整然データ（tidy data）と呼ばれ、pandas や統計ソフトでそのまま扱える形です。

理解度チェック

14日間の記録を保存するテーブルとして、分析しやすいのはどれ？

1行＝1回の記録にすると、日数が変わっても同じ形で集計できます。

Part 2

倫理と個人情報

人からデータを集めるときに、必ず守ることです。

Step 3/ 12

説明と同意

人からデータを集めるときは、参加する人に研究の内容を説明し、自分の意思で参加してもらうことが必要です。これをインフォームド・コンセント（説明と同意）といいます。

説明すること例
研究の目的計算練習の効果を調べるため
やってもらうこと・時間14日間、1日5分の練習と記録
集めるデータ練習の成績と時間。名前は記録しない
データの使い道と保管研究発表に使う。個人が特定できない形で、終了後○年で削除
参加は自由参加しなくても、途中でやめても、不利益はない
問い合わせ先研究者と指導教員の連絡先

注意

大学によっては、人を対象とする研究に倫理審査が必要です。プレゼミの体験レベルでも、どこまで手続きがいるかは指導教員に確認しましょう。参加者が未成年の場合は、保護者の同意も必要になります。

ポイント

同意は、説明文を読んでもらったうえで、紙やフォームで記録を残します。同意した日を participants テーブルの consented_at に入れておくと、同意のない人のデータが紛れ込むのを防げます。

次へ：個人情報を守る

Step 4/ 12

個人情報を守る

研究データには、他人に知られたくない情報が含まれることがあります。集めない・分ける・見せない・消すの4つを意識します。

方針具体的にやること
集めない問いに不要な情報（名前、学籍番号、住所など）は記録しない
分ける名前と ID の対応表は、システムとは別の場所（紙や、ネットにつながない PC）で保管する
見せないデータの一覧は管理者だけが見られるようにする（Step 7）。通信は HTTPS
消す研究が終わったら、決めた期間のあとに確実に削除する

注意

データベースのファイル（research.db）や書き出した CSV は、絶対に GitHub に上げないでください。.gitignore に *.db と *.csv を書いておきます（第2回 Step 10）。

補足

ID に連番（P01、P02…）を使う場合、参加者が他人の ID を推測して入力できてしまいます。気になる場合は、推測しにくい ID（例：K7F2）を配りましょう。その場合は、Step 5 のフォームの pattern と例（P01）も、配った ID の形に合わせて変えます。

1 / 7データの流れ

はじめに、Step 2 の schema.sql と同じフォルダに次のファイルを作り、テーブルを作って参加者を登録します。フォームは登録された ID しか受け付けないので、この準備を忘れると誰も記録できません。

init_db.py
import sqlite3

conn = sqlite3.connect("research.db")
with open("schema.sql", encoding="utf-8") as f:
    conn.executescript(f.read())          # テーブルを作る（すでにあれば何もしない）

# 同意を得た参加者だけを登録する
participants = [
    ("P01", "2026-11-16"),
    ("P02", "2026-11-16"),
]
conn.executemany(
    "INSERT OR IGNORE INTO participants (participant_id, consented_at) VALUES (?, ?)",
    participants,
)
conn.commit()
conn.close()
print("準備ができました")
ターミナル
$ python init_db.py

参加者が増えたら、participants のリストに足して、もう一度実行します（登録済みの ID は二重に入りません）。

app.py（記録の部分）
import sqlite3
from flask import Flask, render_template, request, redirect, url_for

app = Flask(__name__)
DB = "research.db"

def get_db():
    conn = sqlite3.connect(DB)
    conn.row_factory = sqlite3.Row
    return conn

@app.route("/", methods=["GET", "POST"])
def record():
    errors = []
    if request.method == "POST":
        pid = request.form.get("participant_id", "").strip().upper()
        day = request.form.get("day", type=int)
        total = request.form.get("total", type=int)
        correct = request.form.get("correct", type=int)
        seconds = request.form.get("seconds", type=float)
        difficulty = request.form.get("difficulty", type=int)

        with get_db() as conn:
            known = conn.execute("SELECT 1 FROM participants WHERE participant_id = ?", (pid,)).fetchone()
        if not known:
            errors.append("参加者IDが見つかりません。配られたIDを確認してください")
        if day is None or not 1 <= day <= 14:
            errors.append("何日目かは 1〜14 で入力してください")
        if total is None or correct is None or not 0 <= correct <= total:
            errors.append("正答数は 0〜問題数 の範囲で入力してください")
        if seconds is None or seconds <= 0:
            errors.append("かかった時間を秒で入力してください")

        if not errors:
            with get_db() as conn:
                conn.execute(
                    "INSERT INTO records (participant_id, day, total, correct, seconds, difficulty)"
                    " VALUES (?, ?, ?, ?, ?, ?)",
                    (pid, day, total, correct, seconds, difficulty),
                )
            return redirect(url_for("thanks"))
    return render_template("record.html", errors=errors)

@app.route("/thanks")
def thanks():
    return render_template("thanks.html")

補足

request.form.get("day", type=int) は、数字に変換できない値が来たときに None を返します。そのため、数字以外が入力されてもエラーで止まらず、チェックに引っかかります。

次へ：入力ミスと記録漏れを防ぐ

Step 6/ 12

入力ミスと記録漏れを防ぐ

集めたデータの質は、入力のしやすさとチェックで決まります。チェックは2段構えにします。

チェックする場所方法役割
ブラウザ（HTML）required、min、max、pattern入力の段階で、うっかりミスを知らせる
サーバー（Python）Step 5 の if のチェックHTML のチェックは書き換えられるので、最後の砦はサーバー側

管理者は、毎日記録漏れがないかを確かめます。SQL の GROUP BY で、参加者ごとの記録回数をまとめられます。

参加者ごとの記録回数
SELECT participant_id,
       COUNT(*)  AS records,     -- 記録した回数
       MAX(day)  AS last_day     -- 最後に記録した日
FROM records
GROUP BY participant_id
ORDER BY participant_id;
同じ日に2回記録していないか
SELECT participant_id, day, COUNT(*) AS n
FROM records
GROUP BY participant_id, day
HAVING COUNT(*) > 1;            -- 同じ日に2回以上記録している人

ポイント

記録漏れに気づいたら、その日のうちに参加者へ声をかけましょう。数日たつと記憶があいまいになり、正確な記録ができなくなります。

理解度チェック

HTML に required や max を書いたのに、Python 側でもチェックするのはなぜ？

ブラウザから届く値は信用せず、サーバーで必ず確かめます。

次へ：管理者だけが見られるようにする

Step 7/ 12

管理者だけが見られるようにする

全員の記録の一覧や CSV の書き出しは、管理者（研究者）だけが使えるようにします。ここでは第1回の Security 2 で学んだセッションを使って、簡単なログインを作ります。

app.py（管理者の部分）
import os, secrets
from flask import session

app.secret_key = os.environ["SECRET_KEY"]           # セッション用の秘密の鍵
ADMIN_PASSWORD = os.environ["ADMIN_PASSWORD"]       # 管理者のパスワード

def is_admin():
    return session.get("admin") is True

@app.route("/admin/login", methods=["GET", "POST"])
def admin_login():
    if request.method == "POST":
        if secrets.compare_digest(request.form.get("password", ""), ADMIN_PASSWORD):
            session["admin"] = True
            return redirect(url_for("admin"))
    return render_template("login.html")

@app.route("/admin")
def admin():
    if not is_admin():
        return redirect(url_for("admin_login"))
    with get_db() as conn:
        rows = conn.execute(
            "SELECT participant_id, COUNT(*) AS records, MAX(day) AS last_day"
            " FROM records GROUP BY participant_id ORDER BY participant_id"
        ).fetchall()
    return render_template("admin.html", rows=rows)

パスワードや秘密の鍵は、コードに書かずに環境変数で渡します。こうしておけば、コードを GitHub に上げても秘密は漏れません。

ターミナル
# 秘密の鍵を作る（表示された文字列を使う）
$ python3 -c "import secrets; print(secrets.token_hex(32))"

# Mac / Git Bash
$ export SECRET_KEY="さっきの文字列"
$ export ADMIN_PASSWORD="管理者のパスワード"

# Windows（PowerShell）
$ $env:SECRET_KEY="さっきの文字列"
$ $env:ADMIN_PASSWORD="管理者のパスワード"

起動するときの注意

環境変数を設定せずに起動すると、KeyError: 'SECRET_KEY' で止まります。また、この設定はターミナルを閉じると消えるので、サーバーを起動するたびに設定します。

補足

secrets.compare_digest は、パスワードを比べるための安全な方法です。ふつうの == より、比べる時間の差から推測される危険が小さくなります。

注意

この方法は、少人数の研究用の簡単なしくみです。大切な個人情報を大人数から集める場合は、大学の情報部門や指導教員に相談し、より安全なしくみを使いましょう。

次へ：公開して、運用する

Step 8/ 12

公開して、運用する

参加者が自分のスマホから記録できるように、システムをインターネットに公開します。公開の考え方は第3回の Step 14 を見てください。

運用のポイントやること
予備調査本番の前に、2〜3人に数日使ってもらい、わかりにくい点を直す
データが消えない場所か確かめる公開サービスによっては、再起動や更新のたびにファイルがリセットされる。SQLite を使うなら、ファイルが残る設定やサービスを選ぶ

注意

公開したあとは debug=True を必ず外します。エラーの詳細画面から、プログラムの中身が見えてしまうためです。

ポイント

本番の途中でシステムを大きく変えると、前半と後半でデータの意味が変わってしまいます。直す必要が出たら、変えた日と内容を研究ノートに残しましょう。

次へ：CSV に書き出す

Part 4

記録をデータとして取り出し、集計してグラフにします。

Step 9/ 12

CSV に書き出す

データが集まったら、分析のために CSV（カンマで区切った表のファイル）に書き出します。CSV は Excel でも pandas でも開ける、データの共通の形です。

app.py（CSV の書き出し）
import csv, io
from flask import Response

@app.route("/admin/export.csv")
def export_csv():
    if not is_admin():
        return redirect(url_for("admin_login"))
    with get_db() as conn:
        rows = conn.execute("SELECT * FROM records ORDER BY participant_id, day").fetchall()

    buf = io.StringIO()
    writer = csv.writer(buf)
    writer.writerow(["id", "participant_id", "day", "total", "correct", "seconds", "difficulty", "created_at"])
    writer.writerows([tuple(r) for r in rows])

    # 先頭の ﻿ は、Excel で開いても文字化けしないための印
    return Response("﻿" + buf.getvalue(), mimetype="text/csv",
                    headers={"Content-Disposition": "attachment; filename=records.csv"})

次へ：pandas で集計する

Step 10/ 12

pandas で集計する

pandas は、表のデータを Python で扱うためのライブラリです。Excel の集計を、コードで正確にくり返せるようにしたものと考えるとわかりやすいです。

ターミナル
$ pip install pandas matplotlib scipy
analyze.py
import pandas as pd

df = pd.read_csv("records.csv")

# 元の数字から、分析に使う値を計算する
df["accuracy"] = df["correct"] / df["total"]        # 正答率
df["sec_per_q"] = df["seconds"] / df["total"]       # 1問あたりの秒数

print(len(df), "件")
print(df.describe())

# 日ごとの平均
daily = df.groupby("day")[["accuracy", "sec_per_q"]].mean()
print(daily.round(2))

リサーチクエスチョンに答えるために、1日目と14日目を同じ人どうしで比べます。

analyze.py（つづき）
# 1日目と14日目を、人ごとに並べる
first = df[df["day"] == 1].set_index("participant_id")["sec_per_q"]
last = df[df["day"] == 14].set_index("participant_id")["sec_per_q"]
paired = pd.DataFrame({"day1": first, "day14": last}).dropna()

paired["change"] = paired["day14"] - paired["day1"]
print(paired.round(2))
print("平均の変化：", paired["change"].mean().round(2), "秒")
よく使う書き方意味
df["列名"]列を取り出す
df[df["day"] == 1]条件に合う行だけにする
df.groupby("day").mean()グループごとの平均
df.describe()件数・平均・最小・最大などをまとめて表示

ポイント

まず len(df) で件数を確かめ、「10人 × 14日 ＝ 140件」になっているかを見ましょう。足りなければ記録漏れ、多ければ二重記録です。

次へ：グラフにする

Step 11/ 12

グラフにする

数字の表だけでは傾向が見えにくいので、matplotlib でグラフにします。

chart.py
import matplotlib.pyplot as plt

ax = daily["sec_per_q"].plot(marker="o")

平均だけでは、全員が同じように速くなったのか、一部の人だけが大きく変わったのかがわかりません。1人ずつの変化も重ねて描いてみましょう。

chart.py（つづき）
# 1人1本の線で、全員の変化を重ねて描く
for pid, g in df.groupby("participant_id"):
    plt.plot(g["day"], g["sec_per_q"], marker=".", alpha=0.6, label=pid)
plt.legend(ncol=2, fontsize=8)
plt.savefig("each_person.png", dpi=200, bbox_inches="tight")

補足

matplotlib は、そのままでは日本語が四角い記号（豆腐）になって表示されません。ラベルを英語にするか、japanize-matplotlib などで日本語フォントを設定します。

ポイント

グラフには、軸の名前と単位を必ず書きます。「何の、どの単位の数字か」がわからないグラフは、レポートでは使えません。

次へ：考察につなげる

Step 12/ 12

考察につなげる

グラフで変化が見えても、それが偶然の差なのかを確かめる必要があります。同じ人の前後を比べるときは、対応のある t 検定という方法がよく使われます。

analyze.py（つづき）
from scipy import stats

result = stats.ttest_rel(paired["day1"], paired["day14"])
print("p値：", result.pvalue)

補足

p値が小さい（よく 0.05 未満が目安）ほど、「偶然だけでこの差が出たとは考えにくい」ことを表します。ただし、p値は効果の大きさを表すものではありません。何秒短くなったのか、という変化の大きさもあわせて報告します。どの検定を使うべきかは、データの形によって変わるので、指導教員に相談しましょう。

分析の結果が出たら、研究の流れの「考察する」に進みます。

考察で考えることこの例では
仮説と合っているか1問あたりの時間は短くなった。正答率は下がっていない
ほかの説明はできないか同じ形式の問題に慣れただけかもしれない
人による違いもともと速い人はあまり変わらなかった
研究ノートとの照合8日目に全員が遅くなったのは、問題の種類を変えた日だった
限界と次の課題10人と少なく、練習しないグループと比べていない

ポイント

考察から生まれた「次の課題」は、次の研究のリサーチクエスチョンになります。システムも少し直せば、次の研究にそのまま使えます。
